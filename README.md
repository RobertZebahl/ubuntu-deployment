# ubuntu-deployment

PyInfra-based deployment for a fresh Ubuntu install, driven by a
declarative YAML file instead of hand-written PyInfra operations.

> **Note:** This repository is intended for my private use. It was mainly
> generated by [Claude Code](https://claude.com/claude-code) using the
> `grill-me` skill, which interviews the user about a plan before any code is
> written. It is an unofficial setup, not affiliated with or endorsed by
> Anthropic, Canonical or the vendors of the software it installs; the skills
> are third-party ([mattpocock/skills](https://github.com/mattpocock/skills)).
> It comes with no support or guarantees and changes your system with `sudo`,
> so use it at your own risk.

## Requirements

- `git` (to get this repository) and `curl` or `wget`, if your Ubuntu lacks them:
  `sudo apt install git curl`
- Ubuntu 26.04 LTS, the only release supported: several third-party repos
  in `data/entries.yml` are pinned to its codename, `resolute`. On any other
  release (or another distribution) `deploy.sh` stops with a message before it
  asks for your password or changes anything, and `bootstrap.py` and
  `deploy.py` do the same when started directly, `--dry` runs included. The
  release is set in `release.py`; when you move to a new LTS, change it
  together with the pinned repos.

## Usage

```sh
./deploy.sh            # apply, prompting once for your sudo password
./deploy.sh --dry      # preview what would change, without applying
./deploy.sh -y         # apply without the confirmation prompts
```

This runs against `@local` (this machine), the only target: `inventory.py`
defines it, and there is no support for deploying to other machines.

`deploy.sh` needs [uv](https://docs.astral.sh/uv/) to run PyInfra. On a
fresh machine it installs uv itself (with uv's official installer, into
`~/.local/bin`) before anything else, so uv isn't a prerequisite; `git` and
`curl` or `wget` are. `uv run` then creates the project's Python environment
on the first run. The "Update uv" entry in `data/entries.yml` runs
`uv self update` when a newer uv exists (it checks with `--dry-run` first, so
a repeat run reports "No changes" until then). That works for the standalone
install `deploy.sh` makes, not for a uv from pip or apt.

uv is also configured to use only the Python that Ubuntu provides:
`files/uv.toml` (`python-downloads = "never"` and
`python-preference = "only-system"`) is deployed to `~/.config/uv/uv.toml`, so
uv downloads no Python and ignores managed ones (`uv python install`), too.
Ubuntu's `python3` covers this repo's `requires-python`. The entry overwrites
an existing `uv.toml` there. The very first `uv run` in `deploy.sh` happens
before that file exists; uv prefers an installed Python over downloading one
anyway, so it only matters if `requires-python` is raised above what the
system has.

### Two phases

`deploy.sh` runs PyInfra twice: `bootstrap.py`, then `deploy.py`.
PyInfra evaluates every *fact* while it loads a deploy file, before any of
its operations run, so a tool that an entry in `entries.yml` installs isn't
there yet when a fact needs it (e.g. `curl` for the GitHub release lookup
of `github-deb`). The tools those facts need are declared in
`data/entries.yml` like everything else, as `apt` entries marked
`bootstrap: true` (currently `curl`, `git`, `ca-certificates` and `gpg`,
which the signing-key expiry check needs).
`bootstrap.py` applies exactly those entries, and `deploy.py` skips them.
If you add a fact that needs another tool, add that tool to the
`bootstrap: true` entry. `update`, `needs` and `when_gpu` don't apply to
such an entry.

`bootstrap.py` refreshes the package index first (if it's over an hour
old), and carries on if that fails: a broken third-party repository, such as
one whose signing key has expired, makes `apt update` fail, but everything
`bootstrap.py` installs comes from Ubuntu's own archive. The failure is
shown as "Error (ignored)". `deploy.py` is strict about it, see
"Adding a third-party apt repository".

A `--dry` run on a machine without `curl` can't look up a `github-deb`
release, so it prints a warning and skips that entry. A real run never
hits this, since `bootstrap.py` has installed `curl` by then.

### Waiting for apt

Right after a boot or login, background jobs (typically PackageKit,
`update-notifier` and the `apt-daily` timers) run `apt-get` for a while,
and apt fails *immediately* with "Could not get lock
/var/lib/apt/lists/lock" instead of waiting for them. `DPkg::Lock::Timeout`
doesn't help, since it only covers the dpkg lock, not this one. So
`bootstrap.py` and `deploy.py` each start with `wait_for_apt_lock()`
(`aptlock.py`): it checks whether any process has apt's or dpkg's lock files
open (`fuser`) and, only if one does, waits up to 300 seconds for it to
finish. On a quiet machine the step is skipped and shows as "No changes"; it
doesn't stop or reconfigure any service.

The wait happens once per run, not before every apt operation, which would
print a step for each of them. So a background job that starts *during* a
run isn't waited for. If a run fails with a lock error, wait a few minutes
and start it again.

## Repeat runs

After a successful `./deploy.sh`, a second one should report every
operation as "No changes", with two exceptions. The package-index refresh in
`bootstrap.py` runs if the index is more than an hour old. And *track* entries
(see below) report a change once upstream has something newer.

`bootstrap.py` stops at the first error, since everything after it needs
what it installs. `deploy.py` goes on: an entry that fails is shown as
"Error (ignored)" and listed in the Error column of the results, and the
other entries are still applied, so one broken third-party repository doesn't
keep a hundred packages from being installed. An entry that `needs:` a failed
one is skipped, with a warning, rather than run (see below). PyInfra counts
those errors as ignored, so **the exit status is 0 even if entries failed**:
read the results. Fix the cause and run it again; entries that already
succeeded report "No changes". (The apt lock wait at the start of `deploy.py`
is the exception: if the machine stays locked, the run stops there.)

## Entry fields

Every entry has a `name`, and it is unique: `needs:` refers to entries by
name, and so do the results of a run. Loading the file fails if a name is
missing or used twice. Optional fields that keep entries consistent:

- `needs: <entry name>` (or a list) names the earlier entries this one
  depends on (say the `claude-docker` symlink on "Install Docker Engine").
  Loading the file fails if a name isn't an earlier entry. Because the run
  goes on after an error, an entry is skipped, with a warning, instead of
  running anyway if an entry it needs failed, or doesn't apply on this machine
  (its `when_gpu` doesn't match, its `fstab` disk is absent, `curl` is missing
  for `github-deb`), or was itself skipped for one of those reasons. A package
  would otherwise be installed from Ubuntu's own archive when the repository
  entry before it failed, and what builds on a driver that isn't installed
  can't work. So a package entry names the repository entry it installs from.
  The exception is `skip_if_exists`: an entry skipped by it counts as
  satisfied, since something else already provides what it would add (see the
  Steam entries).
- `skip_if_exists: <path>` (any type; `~/` is resolved) skips the entry
  if that path exists when the run starts. It's for a repository that
  something else already provides, see the Steam entries below.

## Adding things to deploy

Edit `data/entries.yml`. Each entry has a `type` that decides how it's
applied:

| type       | what it does                                    | sudo |
|------------|--------------------------------------------------|------|
| `apt`      | system packages (`apt.packages`); package names may use `{kernel_release}` | yes  |
| `apt-repo` | add a third-party apt repository + signing key   | yes  |
| `apt-ppa`  | add an Ubuntu PPA (`apt.ppa`, via `ppa:owner/name`) | yes |
| `github-deb` | install the latest .deb release from a GitHub repo (`apt.deb`) | yes |
| `snap`     | install package(s) via snap (`snap.package`)     | yes  |
| `user-group` | add a user to secondary group(s) (`server.user`) | yes |
| `git`      | clone/pull a git repo (`git.repo`)               | optional |
| `uv-tool`  | isolated CLI tools (`uv tool install`)           | no   |
| `uv-pip`   | importable Python packages (`uv pip install --user`) | no |
| `shell`    | an arbitrary shell command                       | optional |
| `file`     | copy a static file from `files/` (optional `mode: "644"`) | optional |

### Ensure and track

An entry either *ensures* or *tracks*. An **ensure** entry (most of them) makes
sure something is there and then leaves it alone: an installed package stays
at its version even when a newer one exists, so upgrading it is up to you
(`apt upgrade`, `uv tool upgrade`, ...). A **track** entry follows upstream: it
first checks whether something newer exists, applies it if so, and reports "No
changes" otherwise. Track entries are named "Install/Update ..." (before the
first run the thing may not be there), or just "Update ..." if the entry never
installs it: the `git` entries (NERDTree, `claude-docker`), the `github-deb`
entry (Heroic, which needs `package:` for the check) and "Update uv" (uv is
installed by `deploy.sh` already). To keep something current, add such an
entry for it that checks upstream first; nothing else does. (A
tracked `git` checkout takes upstream changes without a review, see
`claude-docker` below.)

### Idempotency

A repeat run should change nothing (track entries excepted, see above), and
that holds as follows:

- `apt`, `apt-repo`, `user-group`, `git`, `snap`, `uv-tool` and `uv-pip` are
  naturally idempotent: PyInfra checks installed-package/repo/file state
  before doing anything.
- `apt` with `update: true` refreshes apt's package index only if an
  `apt-repo`/`apt-ppa` entry changed something earlier in the same run (a
  repo that was just added isn't in the index yet), or if apt has never
  fetched such a repo's package lists (an earlier run died between adding
  the repo and its `apt update`, so its entries report "No changes" now but
  the repo is still missing from the index). Otherwise it doesn't refresh,
  so a repeat run doesn't re-download the package lists.
- `apt-ppa` would re-run `apt-add-repository` every time, so `deploy.py`
  skips it once the PPA's sources file exists.
- `github-deb` is idempotent only if the entry names the installed
  package with `package:`; see the section below.
- `shell` is not idempotent, so it needs an explicit guard:

  - `creates: <path>` — skip if that path already exists.
  - `unless: <shell command>` — skip if that command exits successfully.

Any entry can be restricted to a detected GPU vendor with `when_gpu: amd`
(or `nvidia` / `intel`), evaluated via the custom `GpuVendor` fact in
`deploy.py` (parses `lspci`).

`file` and `git` entries' `dest` may start with `~/` — `deploy.py` resolves
it to the target's real home directory itself (`expand_home()`), since
neither `files.put` nor `git.repo` expand a literal `~` in `dest` on their
own; left alone it silently creates a directory/file named `~` instead.

### Installing the latest release from GitHub as a .deb

Some software (like Heroic Games Launcher) only ships as a .deb attached
directly to GitHub Releases, not through an apt repository. `github-deb`
resolves the latest release via GitHub's API (`GithubLatestDebAsset` fact
in `deploy.py`, which needs the `curl` that `bootstrap.py` installs) and
installs whichever `.deb` asset matches, via `apt.deb`. Use `match` to pick
the right asset when a release publishes more than one .deb (e.g. an arch
tag like `amd64`).

"Latest" is re-resolved on every run. Give the entry `package:` (the name
of the installed package, e.g. `heroic`) and `deploy.py` compares the
release's version (its tag without a leading `v`) with the installed one: a
new upstream release is installed over the old one, and if the same
version is already installed, nothing is downloaded or reinstalled. Without
`package:` the .deb is downloaded and reinstalled on *every* run, because
`apt.deb` can't compare versions for a URL (the file doesn't exist yet
while the run is planned). The comparison assumes the release tag equals the
package's version, which holds for Heroic; check `dpkg-query -W <package>`
for a new entry.

### Building kernel modules

The "Install kernel module build tools" entry installs `build-essential`,
`dkms`, and `linux-headers-{kernel_release}`. That last placeholder is
resolved by `deploy.py` to the target's actual running kernel version
(`uname -r`, via the `KernelVersion` fact) — it can't be a fixed value in
the YAML since it's host- and time-specific and changes on every kernel
upgrade. This covers building/rebuilding out-of-tree modules in general
(e.g. VirtualBox or NVIDIA's DKMS-packaged drivers); it's not needed for
the AMD GPU driver above, which is already built into the kernel.

### Adding a third-party apt repository

Use `apt-repo` (see the Docker example in `data/entries.yml`). It writes a
modern deb822 `.sources` file via `apt.sources_file`, and, if the repo
needs a signing key, fetches it first via `apt.key` (writing to
`/etc/apt/keyrings/`, not the deprecated `apt-key`). A package that
installs *from* that new repo needs `update: true` on its `apt` entry, so
apt re-indexes before looking for the package (only if the repo entry
actually changed something in that run, or the repo isn't in apt's index
yet) — and needs to come after the
`apt-repo` entry in the file, same ordering rule as everything else here.
It also names that entry in `needs:`, so that it is skipped, not run against
Ubuntu's own archive, when the repository entry fails (an expired signing key,
say).

#### Signing keys that expire

`apt.key` leaves an existing key file alone, so on its own it would never
pick up a renewed key. `deploy.py` therefore downloads the key itself
whenever the file at `key_dest` is missing, or holds only expired keys
(checked with `gpg`), and the run fails if the key it just downloaded has
expired too:

> The signing key at `<key_src>` has expired, and upstream has not
> published a renewed one yet. Try again later, or remove the entry ... from
> `data/entries.yml`.

That entry fails, and nothing is written: the repository's `.sources` file
is not added without its key (apt would fail on it at every later
`apt update`), and the package entry that `needs:` the repository is skipped
instead of installing Ubuntu's own version. All other entries are still
applied. A repeat run says the same until upstream publishes a renewed key,
and then installs it without you doing anything. Before this check, an expired key showed up only as apt's
"The repository ... is not signed" at the next `apt update`, which fails
every run that comes after it, including `bootstrap.py`'s (which now only
warns). Of the repos in `data/entries.yml`, only Darktable's (openSUSE
Build Service) key has an expiry date, currently 2026-09-20.

There is deliberately no option to skip signature checks for a repo:
`.deb` packages run scripts as root, and apt has no way to ignore just an
expired key, only to stop verifying the repo altogether.

A keyring with several keys counts as expired only if all of its primary
keys are; a signing *subkey* that expired on its own isn't looked at.

### Adding a PPA

Use `apt-ppa` for a `ppa:owner/name` repository (see the Siril example in
`data/entries.yml`) rather than `apt-repo` — PPAs are resolved by
`apt-add-repository` (from `software-properties-common`, which has its own
entry in `data/entries.yml`; give a PPA entry `needs:` for it), which knows how to translate the short PPA
name into the right Launchpad URL and signing key; `apt-repo` is for
repositories you already have full connection details for. Same ordering
rule applies: the package(s) it provides need `update: true` and must
come after the `apt-ppa` entry. A PPA that is already configured is
skipped, so a repeat run doesn't touch it. Not every PPA has published a build for
every Ubuntu series — check the PPA's Launchpad page for your release
before relying on it, adding the repo will succeed either way but
installing the package will fail if there's no build for your series.

### Steam and its own apt source

Valve's `steam-launcher` package installs its *own* apt source for the same
repository (`steam-stable.list`, with its key at
`/usr/share/keyrings/steam.gpg`). Two sources for one repo that name
different `Signed-By` keys make apt refuse to read its source list at all
("Conflicting values set for option Signed-By"), which fails every apt step
after Steam. So the Steam entries handle this in three steps:

- our `apt-repo` entry writes the key to that same
  `/usr/share/keyrings/steam.gpg`, so the two sources agree;
- a `shell` entry after "Install Steam" removes our now-redundant
  `steam.sources` (otherwise every `apt update` prints "configured multiple
  times" warnings);
- `skip_if_exists: /etc/apt/sources.list.d/steam-stable.list` keeps our
  repo entry from adding it back on the next run.

The same problem can occur with any package that ships its own apt source.
In testing only Steam did: after a run, VS Code and VirtualBox only
had the source their own `apt-repo` entry wrote. If a run fails with
"Conflicting values set for option Signed-By", look for a second source of
the same repo in `/etc/apt/sources.list.d/`.

### Running Docker without sudo

The "Allow running Docker without sudo" entry in `data/entries.yml` adds
you to the `docker` group via `user-group` (which is itself equivalent to
root, since it can bind-mount the whole filesystem into a container — a
deliberate tradeoff for not typing `sudo` on a personal machine, not one
to make on a shared/production host). It defaults to whichever user runs
the deploy; group membership only takes effect in a **new login session**
(log out/in, or run `newgrp docker`) — not in the shell that ran
`deploy.sh`.

### Running Claude Code in Docker (`claude-docker`)

Besides the host install of Claude Code (see below), two entries put
the `claude-docker` script from
[RobertZebahl/claude-docker](https://github.com/RobertZebahl/claude-docker)
on the PATH: a `git` entry clones the repo to `~/.local/share/claude-docker`
(and pulls the latest `main` on every run), and a `shell` entry symlinks the
script to `~/.local/bin/claude-docker`. Because it's a symlink to a
checkout, a change you push to that repo takes effect at the next
deployment run without a review step. An existing regular file at that
path is replaced by the symlink.

Run `claude-docker` from a project's root: it builds a Docker image with
Claude Code and skills on first use and starts it with only that folder
mounted. It needs Docker without sudo (see above), so it works only after
a **new login session**. On a fresh machine `~/.local/bin` is added to
`PATH` by `~/.profile` only if it exists at login, so log out and in once
after the first run for that too.

### Epson scanner driver (Perfection V39)

The Perfection V39 (USB id `04b8:013d`; the V39 II, `013f`, works with the
same driver) needs Epson's Epson Scan 2: the `epsonscan2` driver and the
`epsonscan2-non-free-plugin` firmware package. Epson ships them only as a
bundle download, and its site refuses scripted downloads, so the entry
"Install Epson scanner driver" doesn't fetch anything: the "deb" bundle
(`epsonscan2-bundle-<version>.x86_64.deb.tar.gz`) has to be in this
repository's `files/` directory before you run `./deploy.sh`. The entry
extracts the highest version found there and installs both `.deb` files
together. Epson's license for the plugin (`COPYING.EPSON` in the
`epsonscan2-non-free-plugin` package) forbids distributing the software to
third parties and placing it in a shared environment accessible via a public
network, so don't commit the bundle to a public repository.

Drop a newer bundle next to the old one and the next run upgrades the driver;
an installed driver that is already as new as the bundle is left alone, and
so is one whose bundle is gone. Without a bundle *and* without the driver the
entry fails with a message saying where to get the bundle; like any failed
entry it is shown as "Error (ignored)" and the rest of the run carries on
(see "Repeat runs"). The plugin keeps its own
version (currently `1.0.0.6`), so a bundle with the same plugin version
doesn't reinstall it. Plug the scanner in (again) after the first install so
that the new udev rules apply, and check it with `scanimage -L`.

### Vim: plugins (NERDTree, NERDCommenter) and `~/.vimrc`

See the `data/entries.yml` entries: `vim-gtk3` (provides both `vim` and
`gvim`), then for each plugin a `git` entry cloning it straight into vim8's
native package directory (`~/.vim/pack/vendor/start/<plugin>` — no plugin
manager needed), and a guarded `shell` entry to generate its `:help` tags. The
same pattern works for any other vim8-native plugin. The `git` entries are
track entries: a run pulls upstream changes.

The "Configure vim" entry deploys `files/vimrc` to `~/.vimrc`, **overwriting**
an existing one; edit `files/vimrc`, not the deployed copy. It has to keep
`filetype plugin indent on`, which NERDCommenter needs (the default leader
key makes `\cc` comment a line and `\cu` uncomment it).

In GVim, Ctrl + mouse wheel and Ctrl++ / Ctrl+- change the font size, and
Ctrl+0 goes back to the size it had before the first change (`files/vimrc`:
one point per step, at least 6, in normal, visual and insert mode; Ctrl+= and
the numpad keys work too). It works with the default font, too, if `guifont`
isn't set. GVim reports Ctrl+- as `<C-_>` (only the numpad minus is
`<C-kMinus>`), so `files/vimrc` maps that. Vim in a terminal can't zoom,
since the font belongs to the terminal: GNOME Terminal zooms with Ctrl++,
Ctrl+- and Ctrl+0.

### Claude Code skills and the Node.js requirement

The skills entry runs `npx skills@latest add mattpocock/skills`. That CLI
needs Node >= 22.20. Ubuntu 26.04's own `nodejs` (22.22) would meet that, but
Ubuntu ships npm/npx as separate packages, so the file adds NodeSource's repo
(`apt-repo`, Node 22.x, npm/npx bundled) and installs `nodejs` from it. The
skills command also checks the Node version itself and fails with a clear
message if it's too old. The `skills` CLI prompts interactively by default;
`-g -a claude-code -y` (already in the entry) makes it non-interactive.
`grill-me` and `grill-with-docs` are wrappers around `grilling` and
`domain-modeling`, so all four are installed. Skills don't auto-update: run
`npx skills@latest update -g -y` when you want newer versions.

### Claude Code asks before touching files outside the project

The "Configure Claude Code to ask outside the working directory" entry
deploys `files/claude-ask-outside-cwd.json` as a *managed settings* drop-in,
`/etc/claude-code/managed-settings.d/10-ask-outside-cwd.json`. Managed
settings are root-owned and no user setting, project setting or command-line
flag overrides them; loosening the policy means editing that file with
`sudo` (Claude Code reloads it while running). Claude Code refuses to start
if the file isn't valid JSON or can't be read by you, which is why the entry
sets `mode: "644"`. It doesn't apply inside
the `claude-docker` sandbox, which has its own configuration.

What it sets, and what that means:

- **`blockReadsOutsideWorkingDirectories: true`**: the Read, Grep and Glob
  tools *refuse* to read outside the working directory, without a prompt.
  To let Claude read such a path, add its directory with `/add-dir <path>`
  in the session. Bash commands that read files (`cat`, `ls`, `head`, ...)
  on such a path *prompt* instead. Needs Claude Code 2.1.257 or later.
- **`disableBypassPermissionsMode: "disable"`**: no
  `--dangerously-skip-permissions`; bypass mode skips every prompt, so it
  would defeat the rest of this file.

Writes outside the working directory need your approval in Manual and
`acceptEdits` mode (`dontAsk` mode denies them instead): that is Claude
Code's own behaviour. Auto mode is *not* disabled, and this file sets no
starting mode: on Pro, Max and Team plans auto mode is the built-in starting
mode unless your own settings choose another. In auto mode a classifier
reviews actions instead of you, and reads outside the working directory
run without a prompt unless `blockReadsOutsideWorkingDirectories` is on. So
"always asks" holds only for sessions that aren't in auto mode. To lock it
out, set `disableAutoMode` to `"disable"` in the `permissions` object of that
file (sessions then start in Manual mode); to choose the starting mode
instead, set `defaultMode` there.

Not covered: a Bash command that reads or writes files without naming
them, such as a Python script that opens files itself, isn't checked
against paths. That would need the OS-level Bash sandbox (`/sandbox`),
which isn't enabled here. Removing the entry from `entries.yml` doesn't
delete the file on a machine that already has it, as with any entry.

### Git identity

The "Configure Git identity" entry sets `user.name`, `user.email` and
`init.defaultBranch` with `git config --global`. It changes only those
keys, so the rest of an existing `~/.gitconfig` stays, and it overwrites
different existing values for these three. **If you clone this repo, change
the name and email in that entry** (they appear in its check and in its
commands); they are what your commits get.

### Mounting a disk automatically

`fstab` entries (see the second-hard-disk example in `data/entries.yml`)
only apply if the device exists on the machine, so one file works across
machines. It creates the mount point, ensures the `/etc/fstab` line and
mounts the disk right away if it isn't mounted yet. The line is matched by
device: an existing line for that disk with different options is replaced,
never duplicated, and an identical one is left alone. A failed immediate
mount doesn't abort the rest of the run (it will still mount on next boot).

## Extending to more types

The schema is a flat list of `{type: ..., ...}` entries specifically so
that adding e.g. `snap` or `npm` later is a new `elif` branch in
`deploy.py` plus new entries in the YAML — not a schema redesign.
